# Marauder Mini v3 — "Cosmo" firmware build

This is **ESP32 Marauder v1.17.0** with one behavioural fix applied to the
Marauder Mini v3 (ESP32-C5) display, plus a new boot splash. Everything else is
untouched; no other hardware target's build output changes at all.

Upstream builds the Mini v3 target in a private TFT repository, so this tree
adds the build configuration for that target (it was the only missing piece) and
then makes the display fix.

- Build script: `tools/build_mini_v3.sh`
- Flasher packaging: `tools/package_mini_v3_flasher.py`
- Web flasher: `web-flasher/`
- Artwork generator: `tools/generate_cyber_skull.py`

---

## What was wrong

The Mini v3 panel is 128 x 128. TFT_eSPI's built-in font is 6 x 8 pixels, so a
row holds **21 characters**. Upstream's single-line printer truncated every line
to that width, and several screens emit longer lines:

| line | characters | what the user saw |
|---|---|---|
| `   BSSID: AA:BB:CC:DD:EE:FF` | 27 | `   BSSID: AA:BB:CC:DD` |
| `Setting AP MAC: AA:BB:CC:DD:EE:FF` | 34 | `Setting AP MAC: AA:BB` |
| `IP address: 192.168.4.100` | 24 | `IP address: 192.168.4` |
| `Hardware: Marauder Mini v3` | 26 | `Hardware: Marauder Mi` |

The Follow / device list did something worse: on mini screens it deliberately
printed only the **second half** of the MAC
(`mac_str.substring(mac_str.length() / 2)`), so the visible value was
`DD:EE:FF Tx: 12 4s` — not enough to identify a device.

Screen titles were clipped too. A font 2 title is about 8 px per glyph, so 16
characters fit across 128 px: `SSID Beacon Clone` (146 px) and
`Bluetooth Analyzer` (135 px) both lost their tails.

## What changed

**`esp32_marauder/DisplayLine.{h,cpp}`** — two new host-testable helpers,
`displayLineRowCount()` and `copyDisplayLineRow()`, that split a string into rows
of N characters, honouring embedded newlines. They are pure functions with no
hardware dependency, so they are covered by unit tests that run on the build host.

**`esp32_marauder/Display.cpp`**

- `Display::printWrapped()` prints a string like `println()` but continues
  anything too long on the rows below instead of clipping it. It leaves the
  cursor exactly where `println()` would have, so surrounding layout is
  unchanged. On every target other than the Mini v3 it *is* `println()`.
- `Display::displayBuffer()` splits long scan-output lines into several screen
  buffer rows on the Mini v3. The color macro at the start of a line is carried
  onto each wrapped row so continuation rows keep their color, and the last row
  of a logical line is still space-padded so it erases what was there before.
- `Display::drawCentreTitle()` draws centred titles in font 2, falling back to
  font 1 whenever font 2 would overrun the panel. Only the Mini v3 falls back;
  other targets call it with identical results to the previous code.

**`esp32_marauder/WiFiScan.cpp` / `MenuFunctions.cpp`** — 31 single-line prints
that carry a value too long for the panel now go through `printWrapped()`: AP
info, device info, the station and AirTag lists, the Follow list, GPS data,
SoftAP and upload status. 58 screen titles now go through `drawCentreTitle()`.
The Mini v3 branch of the Follow list prints the **whole** MAC instead of half.

**`User_Setup_marauder_mini_v3.h`** (new) — the Mini v3 panel configuration:
128 x 128 ST7735, BGR order, green tab 3, backlight active low, SPI at 20 MHz.
It clears the `TFT_*` pin defines that `configs.h` carries for this target, which
are inherited from the older Mini / Centauri layout and do not describe this
board.

**`esp32_marauder/Display.h`** — a compile-time guard that refuses to build the
Mini v3 target without that panel configuration:

```c
#if defined(MARAUDER_MINI_V3) && !defined(ST7735_DRIVER)
  #error "MARAUDER_MINI_V3 requires User_Setup_marauder_mini_v3.h (128x128 ST7735_DRIVER)"
#endif
```

**Boot splash** — the Mini v3 boots into a synthwave sunset: banded sky, a large
half-set sun cut by horizontal slits, a neon skyline framing it with lit windows,
and a striped reflection on the water. Under it are the **COSMO** wordmark and the
tagline **"Jacking in..."**, then the version.

The scene is a 128 x 72 run table rather than a pixel buffer, generated by
`tools/generate_boot_scene.py`. Sky bands, tower silhouettes and water are long
horizontal runs, so runs cost about 1.7 KB where a 16-bit image would cost 18 KB,
and it draws as one `drawFastHLine` per run with no intermediate buffer. The
generator asserts full coverage, run bounds, and that the run table round-trips to
exactly the composed image before it writes the header. Windows are placed from a
fixed pattern, so the scene is identical on every boot rather than shimmering.

Other targets keep the existing JCMK logo splash.

## Fixes from the second report

Four problems were reported from the field, plus one hardware question:

| report | cause | fix |
|---|---|---|
| WiFi and Bluetooth counters same color while wardriving | the palette's "success" color was mint `#3FE8B0`, 27 degrees of hue from the accent cyan `#4FE3EE` the BT counter used - indistinguishable at 16 px | success is now a true green, Bluetooth has its own purple family, and the generator refuses any palette with two saturated entries within 30 degrees of hue |
| not enough color variety, inconsistent | a menu of one kind was a rainbow of one-off colors, or (after the first attempt at fixing that) one flat color for the whole menu | 185 `addNodes` colors repainted by family, then refined so no menu uses fewer than two colors: scanners cyan, sniffers pale cyan, attacks split by mechanism (spam red, floods magenta, rogue-AP yellow), Bluetooth purple, GPS green, files orange, choices yellow, fox hunt lime, settings neutral, Back rows de-emphasised |
| GPS screens cut the text off | the date/time and UTC stamps (23-24 chars) went through single-line prints on a 21-character panel | every GPS data line now wraps; the row budget is asserted by `test_gps_layout` so a field added later fails a test instead of disappearing |
| battery indicator | this board defines no battery source at all, and its IP5306's I2C pins are not documented anywhere public | **not implemented - an attempt was reverted, see below.** Bootloader and everything else unaffected |

One further clipping bug was found while fixing the GPS screens and was not in the
report: the **NMEA screen** prints 60-80 character sentences with screen wrapping
disabled for the Mini, so each sentence was cut at 21 characters. That screen's row
accounting was already written to expect wrapped sentences, so `GPS_NMEA_SCRNWRAP` is
now on for the Mini v3 (`MARAUDER_MINI` is left as upstream had it).

The status bar GPS and SD indicators were also made to say more: see "Status bar
indicators" below.


## The neon theme

The whole UI is rethemed to a neon cyberpunk palette: cyan, magenta, amber and
lime on black, with a deep indigo status bar instead of the stock flat grey.

**How it is applied.** The sources now name colors `NEON_<NAME>` instead of
`TFT_<NAME>` (575 call sites across 10 files). `NeonPalette.h` maps each name one
way:

```c
#if defined(MARAUDER_MINI_V3)
  #define NEON_GREEN  marauder::kNeonOk      // 0x4FF3  neon spring green
#else
  #define NEON_GREEN  TFT_GREEN              // unchanged
#endif
```

So the theme is a Mini v3 change only. On every other target each `NEON_` name
expands to the exact stock macro it replaced, so no other board's *colors* change
— `test_neon_theme_offtarget` checks that direction, and that the off-target arm is
not the neon palette. The mapping is deliberately one macro per legacy token name;
collapsing two legacy names onto one macro would have silently changed the value
other targets use.

The text-fitting helpers (`printWrapped`, `drawCentreTitle`, the row-splitting
functions) are shared code rather than `#ifdef`-ed away, so another target's image
does grow — about 1 KB on a full-screen build. Its *behaviour* does not: off the
Mini v3 those helpers are pass-throughs to the same TFT_eSPI call with the same
arguments the original code made (an earlier version of this change hard-coded the
centre as `SCREEN_WIDTH / 2`, which is not `TFT_WIDTH / 2` on landscape panels;
that was caught by building a second target and has been fixed).

**Where the colors come from.** The palette is taken from reference artwork the
user supplied (a synthwave poster). The image was analysed rather than eyeballed:
its saturated pixels were clustered by hue, giving these dominant accents -

| hue | color | share of accent pixels |
|---|---|---|
| magenta/pink | `#ED35BC` | 27.6% |
| cyan | `#45D8E2` | 17.2% |
| rose/red | `#E52565` | 16.4% |
| purple | `#8D6AA3` | 12.2% |
| yellow | `#F4C139` | 9.6% |
| orange | `#F09651` | 8.5% |
| blue-grey | `#39516E` | 5.5% |
| mint/teal | `#4EACA0` | 1.4% |

Those hues are what the palette is built from. Three of the artwork's own colors are
too dark to read on a black panel (the blue-grey and the purple especially) and it has
almost no green at all, so those entries are lifted or supplied while staying in the
artwork's families.

**Rule 1: every color must be readable as text.** This is the rule that matters, and
getting it wrong is what shipped an earlier build's unreadable text.
`MenuFunctions::getColor()` hands these colors to *menu labels*, so each one is drawn
color-on-black when its row is unselected and black-on-color when it is selected.
Contrast is symmetric, so a single floor - 4.5:1 against black - covers both cases, and
there is no such thing as a color that is "only a background". An earlier version of
this palette exempted two dark entries as fills, and `TFTNAVY` - which upstream uses as
the *text* color for "Add SSIDs", "Select APs" and "Save APs" - landed at **1.33:1**,
invisible in both states.

**Rule 2: saturated colors must be far apart in hue.** Two entries about ten degrees
apart in hue read as one color on a 128 px panel. That is exactly how the wardriving
screen ended up with a WiFi counter and a Bluetooth counter that looked the same:
mint-green (`#3FE8B0`, hue 157) and cyan (`#4FE3EE`, hue 184) are 27 degrees apart and
indistinguishable at 16 px. Nothing in the palette is now within 30 degrees of anything
else. The generator fails loudly on a violation - it caught orange against yellow at 19
degrees while this palette was being rebuilt.

| role | color | on black | hue |
|---|---|---|---|
| body / menu text | `#EAF7FF` | 19.4:1 | neutral |
| accent - scanners, WiFi, hints (image cyan) | `#4FE3EE` | 13.5:1 | 184 |
| success - WiFi frames, GPS (hacker green) | `#4DFF7A` | 15.9:1 | 136 |
| warning - files, SD, uploads (image orange) | `#FF8C55` | 9.2:1 | 21 |
| error, attacks, deauth (cyberpunk red) | `#FF3355` | 5.8:1 | 350 |
| highlight - recon, selection (image magenta) | `#ED4FD0` | 6.7:1 | 309 |
| attention - choices, confirm (image yellow) | `#FFE633` | 16.7:1 | 53 |
| info - wardriving, status (image blue-grey, lifted) | `#7FA8FF` | 9.0:1 | 219 |
| fox hunt, geofences (warning lime) | `#A6F53C` | 16.0:1 | 86 |
| Bluetooth (image purple, lifted) | `#B071F0` | 6.7:1 | 270 |
| sniffers, passive capture (pale cyan tint) | `#9FE4FF` | 15.3:1 | 195 (low sat) |
| configuration, settings (neutral) | `#CFDCEE` | 15.4:1 | neutral |
| **Back / exit rows** (de-emphasised) | `#93A2C0` | 8.2:1 | neutral |

Where two legacy names mean the same kind of thing they now share one color, so that
items of a kind read identically: `TFTNAVY`/`TFTBLUE`, `TFTVIOLET`/`TFTPURPLE`,
`TFTMAROON`/`TFTRED`, `TFTPINK`/`TFTMAGENTA`, `TFTGOLD`/`TFTYELLOW`,
`TFTDARKCYAN`/`TFTCYAN`, `TFTDARKGREEN`/`TFTGREEN`, `TFTOLIVE`/`TFTGREENYELLOW`/`TFTLIME`.

`tools/generate_neon_palette.py` computes those ratios and **refuses to emit a
palette** where body text drops below 10:1, *any* entry falls below 4.5:1 in either
direction, or two saturated entries sit within 30 degrees of hue.
`test_neon_palette` re-checks the numbers from the host, that the palette is genuinely
more than one hue family, and that the WiFi and Bluetooth roles are not in the same hue
sector again.

**Which color goes where.** The point of the scheme is that a color means something,
so the same kind of thing is always the same color:

| where | colors |
|---|---|
| main menu | Recon magenta, WiFi green, Bluetooth purple, GPS green, Device blue |
| WiFi scanners / AP lists | cyan |
| WiFi sniffers, probe/station select | pale cyan |
| anything that transmits - beacon and frame spam | red |
| attacks that flood or disrupt (deauth, SAE, assoc sleep, channel switch) | magenta |
| rogue-AP and social attacks (Evil Portal, Karma, Bad Msg) | yellow |
| BLE: Apple pop-up spam / tag attacks (Spoof Airtag, FindMy Sound) | lime / magenta |
| Bluetooth (menus and sniffers) | purple |
| GPS, wardriving, geofences | green |
| files, SD, save/load/upload | orange |
| choices and confirmations | yellow |
| fox hunt | lime |
| settings, device, info | neutral silver |
| Back / exit rows, everywhere | de-emphasised grey |

Within the menu tree this is a deliberate reassignment: 185 of the 246 `addNodes`
colors were repainted so that a menu of one kind is one color. A blanket sweep was
tried first and reverted - its keyword matching hit the substring `ble` inside
`text_table1`, repainted the whole top-level menu, and made WiFi and Bluetooth the same
color again, which is the exact bug being fixed. The shipped version leaves the root
menus alone, preserves every author's red "danger" node, and protects the settings
toggle nodes (`icon == SETTINGS && color == TFTLIGHTGREY` is load-bearing: seven places,
including navigation, branch on it).

The wardriving screen is now role-colored too: WiFi frames green, Bluetooth frames
purple, Flock detections red, satellite count cyan, and the log file name and size
orange.

The panel is driven with native RGB565 (this firmware builds no sprites and never
calls `setColorDepth`), so a color constant reaches the display as written.


## Status bar indicators

The Mini v3 status bar is 128 px wide, so every indicator has to earn its space. Left to
right: **GPS**, channel, DRAM percentage, and **SD**.

**GPS** now has three states and is always drawn. It used to be two states *and* drawn
only when a module was detected, so a missing GPS module and a module that simply had no
satellite lock both showed nothing:

| state | color |
|---|---|
| no module detected (wiring or power) | red |
| module present, no fix yet (looking at the sky) | amber |
| fix - the position can be trusted | hacker green |

**SD** is green once the card has initialised and red when it has not, which is what a
failed `initSD()` should look like at a glance rather than only at the first failed save.
While making that explicit, a latent bug was fixed: `the_color` was read by the screen
path without ever having been assigned on a board without `HAS_SD`, so the label was
drawn in whatever was on the stack. It is now initialised, and the SD label is only drawn
where `HAS_SD` is defined.

## Battery indicator

**Not implemented, deliberately.** The `%` slot between the DRAM figure and SD stays empty.
This board ships no charge reporting and the status bar is unchanged.

**Why, and what was tried.** The Mini v3 has a LiPo with onboard charging, and the upstream
`Battery` wiki page says charging is done by an "INJOINIC IP5306 I2C". The companion `IC
Connections` page gives the detail — I2C on `GPIO33`/`GPIO22`, address `0x75`, register
`0x78` returning 25/50/75/100% in four steps, polled every 3000ms. **Those pages describe
the WROOM-generation Marauder, not this board:** a C5 has no `GPIO33`, and the Mini v3's own
wiki page names neither the part nor any pins.

A build was made that enabled the IP5306 driver and *searched* for the bus at boot, with
three filters (spare pins only; only pins an external pull-up holds high; and only accepted
if `0x75` answers with a documented register value). **It broke the device on first flash,
so it was reverted.** The lesson is worth keeping: the probe was designed to fail safe
against a *wrong reading*, but it could not be safe against a *wrong pin*. Driving GPIOs
that the firmware has not claimed still reaches whatever the board has wired to them, and no
amount of validation afterwards undoes that. Anything that needs the bus pins needs the
schematic, not a search.

What is left of that work in this tree: nothing. `HAS_BATTERY` is off for the target, the
discovery code is gone, and `BatteryLevel.h` and its tests were deleted rather than left
behind as dead code.

**If you want this later**, the two things that make it safe are the pin numbers — from a
schematic, a continuity check, or the vendor — after which it is two lines in the Mini v3
block of `configs.h`:

```c
#define HAS_BATTERY
#define HAS_IP5306
#define I2C_SDA n
#define I2C_SCL n
```

with upstream's own IP5306 driver doing the rest.


## Screen brightness

**Device > Brightness.** Up or right brightens, down or left dims, and the centre
button saves and returns. The level is applied to the backlight as it changes, so the
effect is visible while choosing, and it is written to NVS only on save, so it survives
a reboot.

Upstream already has this setting and a PWM backlight path, but both are behind
`#ifndef HAS_MINI_SCREEN` - the existing screen is touch driven ("tap the top to
brighten"), and the Mini v3 has no touch. So this is the same feature implemented for
the Mini v3's 5-way switch:

- The PWM/LEDC path now covers the Mini v3 as well as the full-screen targets. The
  other mini screens (M5StickC, Cardputer) keep the plain digital on/off fallback,
  because they have no dimmable backlight pin.
- The Mini v3 backlight is **active low** - upstream's own non-PWM fallback drives the
  pin HIGH to switch it off - so the PWM duty is inverted, otherwise every level would
  run backwards.
- The level table, the LEDC API version handling and that inversion stay in one place
  (`esp32_marauder.ino`); the settings screen asks for levels through accessors rather
  than keeping a second copy.
- `await`-for-release always follows a `justPressed()` on that same button:
  `Switches::justReleased()` reports the pressed -> released edge exactly once, so
  waiting on a button that was never pressed would never return.

## Build

```sh
arduino-cli core install esp32:esp32@3.3.4
tools/build_mini_v3.sh                 # writes ../miniv3-build/out/
```

Target: `esp32:esp32:esp32c5:FlashSize=8M,PartitionScheme=default_8MB,PSRAM=enabled`,
`-DMARAUDER_MINI_V3`, the same pinned library revisions the release workflow
uses, and TFT_eSPI from the ESP32-C5 port (`H4W9/TFT_eSPI`, branch `ESP32-C5`).

On Apple silicon this needs Rosetta 2 — arduino-cli generates `.ino` function
prototypes with a bundled x86_64 `ctags`, and substituting a native ctags
produces corrupt prototypes rather than working ones:

```sh
softwareupdate --install-rosetta --agree-to-license
```

## Web flasher

```sh
cd web-flasher && python3 -m http.server 8000
# open http://localhost:8000/ in Chrome or Edge
```

Two buttons:

- **Application update** — writes the application at `0x10000` and the OTA data
  segment at `0xE000`. Settings, credentials, logs and Evil Portal templates are
  preserved. The OTA data segment is included so a device whose boot slot points
  at `app1` cannot keep booting the old firmware from there.
- **Full install** — bootloader, partition table, OTA data and application.
  Replaces everything on the flash.

ESP Web Tools 10.4.0 is vendored under `web-flasher/vendor/`, so the page works
without internet access. The merged `*-factory-8MB.bin` is also there for
Espressif's Flash Download Tool or `esptool`.

To go back to stock, flash the official
[v1.17.0 Mini v3 release](https://github.com/justcallmekoko/ESP32Marauder/releases/tag/v1.17.0).

## Verification

Proven here, without the device:

- The firmware compiles clean for the Mini v3 target and fits the application
  slot with 40% to spare.
- **`bootloader.bin`, `partitions.bin` and the OTA data image are byte-identical
  to the images upstream publishes for this exact target.** The bootloader is
  produced from the flash size, mode, frequency and PSRAM options, and the
  partition table from the partition scheme, so matching bytes prove the build
  configuration matches the official one — the application will land in the right
  slot on the real partition table.
- The merged 8 MB image built here is byte-identical to the one arduino-cli
  produces from the same build, and carries the application at `0x10000`
  (`0xE9` ESP image header).
- The built application contains the `COSMO` wordmark, the `ESP32 Marauder` and
  `Initializing...` strings, the exact skull bitmap bytes, the `v1.17.0` version
  string and the `Marauder Mini v3` hardware name.
- 121 native unit tests pass: 20 cover the line-wrapping helpers, 6 the splash
  layout (bands disjoint, nothing off-panel), 9 the neon palette (contrast, mapping,
  hue spread, plus a regression test naming the menu colors that were unreadable) and
  2 the off-target color mapping.
- **The retheme does not reach other targets.** `test_neon_theme_offtarget` compiles
  the off-Mini-v3 arm of `NeonPalette.h` and asserts every one of the 23 color names
  expands to the exact stock TFT_eSPI value, and that none of them resolves to a neon
  entry. It also runs the check in the other direction, so a color name that lost its
  mapping would fail rather than silently change another board's palette.
- **A second target was built to check for collateral damage**, and it earned its
  keep: the first version of the title helper centred on `SCREEN_WIDTH / 2`, which is
  not `TFT_WIDTH / 2` on landscape panels, so it would have re-centred every screen
  title on the M5StickC, Cardputer and similar. The helper now takes the centre
  explicitly and reproduces the original call exactly. The same build also showed the
  title call sites that only compile for full-screen targets, which the Mini v3 build
  had been hiding.
- The boot screen composition was re-rendered from the generated scene header at
  128 x 128: title rows 1-8, scene 10-81, COSMO 83-98, "Jacking in..." 101-108,
  version 111-118, nothing overlapping and nothing past row 118 of 128.
- The flasher page was loaded in a real browser: the custom element upgrades, the
  vendor module loads, both manifests parse, the file table renders from
  `files.json`, and all four flash segments are reachable at the published
  offsets with the expected sizes.

**Not** proven, and worth knowing before you flash:

- **The panel pin map is the highest-risk unknown.** 128 x 128 and ST7735 come
  from upstream's own test asserting the Mini v3 resolution, but the pin
  assignments (`MOSI 7`, `SCLK 6`, `CS 23`, `DC 24`, `RST -1`, `BL 5`) come from a
  public third-party Mini v3 build, because upstream's own configuration for this
  target is in a private repository. If those pins are wrong the board will run
  correctly but the screen will stay dark or show nothing useful. `configs.h`
  even carries a *different* pin set for this target, inherited from the older
  Mini.
- Nothing here was run on hardware. RF behaviour, GPS, SD and the boot splash's
  appearance on the real panel are unverified.
- The brightness screen is a blocking button loop, so it has no unit test; its button
  handling and the PWM polarity are unverified. The polarity is not a guess - upstream's
  own non-PWM fallback drives the Mini v3 backlight pin HIGH for off, which is what the
  inversion in `BL_DUTY` follows - but if the panel dims when you press up, that
  inversion is the single line to flip.
- If the screen does not come up, flash the official v1.17.0 release to restore
  the stock firmware; the flash layout is identical, so recovery is the same
  operation in reverse.

## Reverting

```sh
git checkout -- esp32_marauder/ User_Setup_Select.h test/
git clean -f User_Setup_marauder_mini_v3.h esp32_marauder/CyberSkullBitmap.h
```

The changes are confined to the display path and are all guarded by
`MARAUDER_MINI_V3`, so no other target's firmware changes.
